# Регламент самостоятельного тестирования и приемки Case 3

**Назначение:** обязательный рабочий регламент для агента, который вносит изменения в систему ИОТ. Этот документ дополняет `UX_AUDIT_CASE3.md` и `FUNCTIONAL_ACCESS_AUDIT_CASE3.md`.

## Главный принцип

Агент не завершает задачу после изменения кода, успешной сборки или одного ручного клика. Работа считается завершенной только после запуска полного runtime, проверки реальных пользовательских путей, визуальной проверки скриншотов, проверки API и устранения всех найденных критичных дефектов.

Если для реализации или проверки не хватает реальных учетных данных, ролей, ключей моделей, тестовых сотрудников, прав доступа или иной входной информации, агент не имитирует поведение моковыми данными. Он фиксирует точный блокер, уже выполненные проверки и требуемые входные данные.

## Запреты при проверке

- Не заменять backend-ответы моками, статическими JSON или «красивыми» демонстрационными карточками.
- Не считать offline-режим проверкой production-сценария.
- Не считать screenshot достаточным доказательством работы функции.
- Не считать успешную сборку достаточным доказательством корректности интерфейса.
- Не отключать валидацию, авторизацию, обработку ошибок или ограничения ради прохождения happy path.
- Не оставлять известный P0/P1 дефект без исправления или без четко описанного внешнего блокера.

## Подготовка среды

1. Проверить текущую ветку и незакоммиченные изменения. Не откатывать изменения пользователя.
2. Прочитать `README.md`, `RELEASE_GATE.md`, `UX_AUDIT_CASE3.md` и `FUNCTIONAL_ACCESS_AUDIT_CASE3.md`.
3. Проверить конфигурацию `.env` и убедиться, что секреты не выводятся в логах или итоговом отчете.
4. Сначала поднять базовый production-стек без модели: frontend, API Core, AI driver и базу данных. Убедиться, что `qwen-local` отсутствует, а не находится в ошибочном состоянии.
5. Проверить health-check и OpenAPI каждого сервиса.
6. Создать отдельные тестовые учетные записи для каждой доступной роли. Не использовать реальные персональные данные без разрешения.
7. Выполнить `./scripts/no_ai_runtime_smoke.sh`: не-ИИ функции должны работать, `/models/availability` должен сообщать `operating_mode=no-ai`, а генерация — возвращать `MODEL_UNAVAILABLE` без создания задачи.
8. Для приёмки генерации отдельно подключить требуемую реальную модель/провайдера. Недоступность LLM не является отказом всей платформы, но тест без неё нельзя называть проверкой качества генерации.

## Обязательные уровни проверки

| Уровень | Что проверяется | Доказательство |
|---|---|---|
| Static | lint, типы, сборка, миграции, конфигурация | Логи успешного запуска команд |
| API | коды ответов, схемы, авторизация, права, ошибки | Запросы с разными ролями и сохраненные результаты |
| Runtime | взаимодействие frontend, API, AI driver и БД | Реальные созданные задачи и сохраненные отчеты |
| UX | понятность задач, иерархия, отсутствие перегрузки | Скриншоты и чек-лист внешнего аудита |
| Responsive | desktop и mobile, фокус, переполнение | Скриншоты заданных viewport |
| Regression | все существующие функции после изменений | Пройденный сценарный чек-лист |

## Обязательные пользовательские пути

### 1. Гость и авторизация

1. Открыть защищенный URL без токена.
2. Убедиться, что пользователь перенаправлен на вход и данные не отображаются до авторизации.
3. Проверить неверный пароль, отсутствующее поле, просроченную сессию и logout.
4. Проверить регистрацию только в допустимом окружении. В production-подобном контуре убедиться, что действует выбранная политика приглашения/SSO/запрета регистрации.
5. Убедиться, что технические сообщения, токены и stack trace не показываются пользователю.

### 2. Сотрудник (`Employee`)

1. Войти под учетной записью сотрудника.
2. Проверить, что первым открывается «Моя траектория» или корректное пустое состояние, а не общий реестр.
3. Убедиться, что сотрудник не видит и не может найти другого сотрудника через UI, прямой URL или API.
4. Проверить свой профиль, историю обучения, создание/повторный запуск ИОТ в пределах разрешенного сценария.
5. Открыть результат, этапы, карточку курса, ограничения и доказательства.
6. Проверить PDF/XLSX/JSON-экспорт своего отчета.
7. Проверить, что ссылка на чужой отчет, ID задачи или employee ID возвращает 403/404 без раскрытия данных.

### 3. Методист (`Methodist`)

1. Войти под учетной записью методиста.
2. Проверить стартовый экран «Мои сотрудники»/рабочие кейсы, а не загрузку полного реестра.
3. Выполнить поиск по ФИО, должности и ведомству.
4. Проверить, что до ввода минимального количества символов нет массовой выдачи.
5. Проверить ограничение результатов и отсутствие не закрепленного сотрудника в выдаче.
6. Открыть разрешенного сотрудника, проверить профиль и историю, сформировать ИОТ.
7. Проверить статус очереди: `Queued`, `Processing`, `Completed`, `CompletedWithLimitations`, `Failed` - в соответствии с фактической реализацией.
8. Проверить историю, архивирование, разархивирование, переименование и экспорт разрешенного отчета.
9. Попытаться открыть профиль и отчет сотрудника вне назначения через UI и API. Доступ должен быть запрещен.

### 4. Администратор (`Admin`)

1. Войти под администратором.
2. Проверить отдельный административный контур, а не смешение с конструктором ИОТ.
3. Проверить создание/деактивацию учетной записи, назначение роли и закреплений, если эти функции реализованы.
4. Проверить импорт реестра и каталога на валидном и невалидном файле.
5. Проверить, что операции аудируются: кто выполнил действие, когда, над каким ресурсом, с каким результатом.
6. Проверить, что администратора не освобождают от авторизации, валидации и журналирования.

### 5. Формирование ИОТ по профилю

1. Проверить обязательные поля, недопустимые значения, длинные строки, пустую историю и заполненную историю.
2. Проверить выбор каждой доступной модели. Недоступная модель должна быть недоступна для запуска либо возвращать понятное контролируемое состояние.
3. Запустить ИОТ реальными данными и дождаться терминального статуса.
4. Проверить, что в рекомендации нет уже пройденных курсов и нет курсов вне каталога.
5. Проверить этапы, длительность, основания, компетенции, источники и ограничения на соответствие фактическому ответу API.
6. Повторить запрос с тем же idempotency key/двойным кликом и убедиться, что не создаются дубликаты.

### 6. Формирование ИОТ из файлов

1. Проверить JSON, XLSX, XLS, CSV и ZIP в тех форматах, которые заявлены системой.
2. Проверить пустой файл, неверное расширение, неверную схему, поврежденный архив, вложенный архив, слишком большой файл и несколько файлов.
3. Убедиться, что ошибка объясняет проблему без раскрытия серверного пути или стека.
4. Проверить пакет с несколькими профилями: пользователь явно выбирает нужный результат, а система не подставляет первого сотрудника как единственный.
5. Проверить очистку временных файлов после успеха и ошибки.

### 7. AI/fallback и качество результата

1. Проверить штатный запуск без моделей и облачных ключей командой `./scripts/no_ai_runtime_smoke.sh`.
2. Убедиться, что недоступная модель блокирует запрос до очереди: HTTP `503`, `code=MODEL_UNAVAILABLE`, новый task отсутствует.
3. Подключить реальную модель и проверить успешную генерацию отдельно.
4. Имитировать потерю уже подключённой модели контролируемым способом в тестовой среде.
5. Если pipeline допускает fallback после начала обработки, проверить, что результат получает `CompletedWithLimitations` или согласованный статус, содержит `generation_mode`, `quality_status`, ограничения и не маскируется под полноценный LLM-анализ.
6. Проверить утвержденное продуктовое правило: подтверждение методиста или запрет передачи/экспорта degraded-результата.
7. Проверить отсутствие выдуманного радара, бенчмарка или статистики при отсутствии реальных данных.

### 8. История, отчет и экспорт

1. Создать минимум один успешный, один degraded и один неуспешный отчет.
2. Проверить фильтрацию, поиск, архив, разархивирование, переименование и открытие результата.
3. Проверить PDF, XLSX и JSON: файл создается, открывается, содержит именно данные текущего отчета и не содержит чужих данных.
4. Проверить экспорт при отсутствии прав, ошибке сети и пустом результате.
5. Проверить, что экспорт не обещает форматы, которых система не поддерживает.

### 9. Каталог, бенчмарки и настройки

1. Проверить поиск, фильтры и открытие реальной программы в каталоге.
2. Проверить, что бенчмарки показываются только из доступных реальных данных и корректно объясняют отсутствие выборки.
3. Проверить настройки темы, плотности, размера текста, доступности и их сохранение после перезагрузки/повторного входа.
4. Проверить keyboard navigation, visible focus, контраст и работу без мыши.

## Проверка API и безопасности

Выполнить запросы минимум в четырех состояниях: anonymous, employee A, employee B, methodist с ограниченной областью доступа, admin.

- Anonymous не получает данные ни одного защищенного endpoint.
- Employee A не читает профиль, отчет, статус задачи и экспорт Employee B.
- Methodист не читает не закрепленного сотрудника.
- Пользователь не вызывает `/admin/*`.
- Все запросы, использующие ID ресурса, проверяют доступ на backend, а не скрываются только в UI.
- API не возвращает секреты, токены, пути файлов, stack trace и полные персональные данные в ошибках.
- Проверить rate limiting для login, регистрации и тяжелых запусков генерации, если он заявлен/реализован.
- Проверить CORS только для разрешенных origin production и development.

## Визуальная и UX-проверка по скриншотам

Агент обязан самостоятельно открыть приложение в браузере и снять скриншоты реального runtime, а не статической верстки.

### Обязательные viewport

- 1440 x 900: рабочий desktop.
- 1366 x 768: распространенный laptop.
- 768 x 1024: tablet.
- 390 x 844: mobile.

### Обязательные экраны для скриншотов

1. Вход.
2. Первый экран сотрудника.
3. Первый экран методиста.
4. Поиск сотрудника с реальными результатами.
5. Конструктор ИОТ в каждом из трех режимов: из профиля/реестра, новый профиль, файл.
6. Генерация ИОТ.
7. Готовый результат с реальными курсами.
8. Degraded/fallback-состояние.
9. Каталог.
10. Бенчмарк/аналитика с данными и без данных.
11. История и архив.
12. Настройки доступности.

### Внешний UX-аудит каждого скриншота

Для каждого экрана агент должен ответить письменно:

1. Понятно ли за 5 секунд, где пользователь находится и что может сделать дальше?
2. Есть ли одно визуально главное действие?
3. Есть ли элементы, которые конкурируют с главным действием, повторяют друг друга или не влияют на текущую задачу?
4. Нет ли длинного технического текста, названий агентов, служебных кодов или непонятных терминов в основном потоке?
5. Не вложены ли карточки друг в друга, не слишком ли много бейджей, плашек, теней и рамок?
6. Читаются ли заголовок, основной текст, статус и предупреждение как разные уровни?
7. Нет ли обрезанного текста, наложений, горизонтальной прокрутки, прыжков layout или недоступных кнопок?
8. На mobile удобно ли нажимать элементы и закрывать меню/модальные окна одной рукой?
9. При ошибке ясно ли, что произошло и какое безопасное действие доступно пользователю?
10. Есть ли на экране реальные данные и честные ограничения, а не замаскированные заглушки?

Любое отрицательное или неуверенное «нет» требует исправления и повторного screenshot-прохода.

## Цикл работы агента

1. Изучить требования и существующий runtime.
2. Сделать минимально необходимое изменение.
3. Запустить lint, build, unit/integration tests и миграции.
4. Поднять runtime заново, исключив проверку устаревшего контейнера или старого frontend build.
5. Пройти затронутые пользовательские пути через браузер.
6. Снять скриншоты на обязательных viewport.
7. Провести внешний UX-аудит по чек-листу выше.
8. Исправить каждый найденный P0/P1 дефект.
9. Повторить тесты и скриншоты после исправлений.
10. Только после отсутствия известных P0/P1 дефектов пройти полный регрессионный чек-лист и подготовить отчет.

Агент не должен останавливаться на сообщении «build passed». Он продолжает цикл до достижения критериев приемки или до внешнего блокера, который невозможно безопасно обойти.

## Формат итогового отчета агента

1. Список измененных файлов и краткий смысл каждого изменения.
2. Команды запуска и результаты lint/build/test/migration.
3. Адреса поднятого runtime и версии реально запущенных сервисов.
4. Таблица всех пользовательских путей: `пройден / не пройден / заблокирован`, доказательство, найденные дефекты, исправление.
5. Скриншоты по всем обязательным экранам и viewport с реальными данными.
6. Результаты API authorization-тестов для каждой роли.
7. Список fallback/ошибочных сценариев и подтверждение их честного отображения.
8. Перечень оставшихся ограничений. Для каждого: причина, риск, чего именно не хватает от владельца продукта/инфраструктуры.
9. Итоговое утверждение «готово к production» разрешено только при закрытых P0/P1 и выполненном `RELEASE_GATE.md`.

## Definition of Done

Работа завершена только когда:

- Все доступные реальные функции работают в полном runtime.
- Все роли и ресурсные ограничения проверены с отрицательными тестами.
- Полный реестр не появляется ни для сотрудника, ни при первом входе методиста.
- Нет моковых данных, скрытых fallback-ошибок и ложного статуса успешного AI-анализа.
- UI проверен по скриншотам desktop, tablet и mobile; известные проблемы перегрузки, масштабирования и видимости устранены.
- Нет известных P0/P1 дефектов.
- Lint, production build, миграции и обязательные automated tests проходят.
- Итоговый отчет содержит проверяемые доказательства, а не только утверждение о готовности.
