# Функциональный аудит и ТЗ: роли, доступ и пользовательские пути

**Назначение:** документ для агента, который исправляет функциональную модель приложения Case 3.

**Главная цель:** связать учетные записи с реальными правами и профилями сотрудников, исключить выдачу всего реестра после входа, сохранить текущие возможности формирования ИОТ и сделать работу с персональными данными безопасной.

**Актуализация 23 августа 2026 года:** разделы с исходными дефектами ниже сохранены как история аудита и целевое ТЗ. Они не описывают текущий runtime целиком. Фактический статус после выполненных исправлений приведён отдельно и подтверждён `QA_EXECUTION_REPORT_CASE3.md`.

## Границы задачи

- Не добавлять фиктивные профили, отчеты, показатели или рекомендации.
- Не менять правила формирования ИОТ, состав каталога, форматы экспорта и существующие реальные данные без отдельного продуктового решения.
- Не удалять сценарии создания ИОТ, загрузки файлов, истории, каталога, бенчмарков и экспорта.
- Не считать интерфейсным решением замену большого списка на более красивый список. Проблема в правах доступа и неверной модели пользователя.
- Перед включением production-режима требуется решение владельца продукта: первый релиз обслуживает только методистов или одновременно сотрудников и методистов. Ниже описана модель для обоих типов.

## Исходное поведение до исправлений

1. Пользователь регистрируется или входит через `/api/v1/auth/register` и `/api/v1/auth/login`.
2. При выдаче JWT каждому пользователю назначается одна и та же роль `Methodist`.
3. Frontend не получает роль как отдельную часть модели сессии и не строит маршрут в зависимости от нее.
4. Конструктор ИОТ открывается с активным режимом `existing`.
5. При открытии конструктора одновременно запрашиваются полный реестр сотрудников и полный каталог.
6. Первый профиль из ответа автоматически подставляется в форму.
7. В dropdown показываются ФИО, должность, ведомство и количество курсов каждого сотрудника.
8. Пользователь может запустить формирование ИОТ, открыть историю, экспортировать отчет.

Следствие: учетная запись пользователя и профиль сотрудника не связаны. Любой вошедший пользователь попадает в сценарий выбора из общего реестра вместо работы со своим или закрепленным набором людей.

## Текущее подтверждённое состояние

1. Роль хранится в таблице `users`, попадает в JWT и возвращается через `GET /me`; новая свободно зарегистрированная учётная запись получает роль `Employee`, а не `Methodist`.
2. Глобальное `MapControllers().RequireAuthorization()` закрывает все controller-endpoint, кроме явно помеченных `[AllowAnonymous]` login/register; health также явно публичен.
3. `GET /analysis/users` доступен только роли `Admin`. Employee и Methodist получают 403; frontend запрашивает реестр только после подтверждения роли Admin.
4. Конструктор по умолчанию открывает нейтральный режим нового профиля (`custom`) и не выбирает первого человека из реестра.
5. Status, history, rename, archive и unarchive фильтруются по `UserId`. Воспроизводимый `scripts/qa_acl_smoke.sh` доказал изоляцию Employee A → Employee B: чужой ресурс возвращает 404 и отсутствует в history.
6. Fallback имеет `generation_mode=fallback`, `quality_status=degraded` и статус задачи `CompletedWithLimitations`; frontend запрещает экспорт такого результата.
7. Задачи сохраняются в PostgreSQL и обрабатываются `AnalysisQueueWorker`; восстановление после рестарта и поведение попыток проверены runtime-тестом.
8. Не реализованы без решения владельца продукта: связь Employee ↔ профиль, назначения Methodist, отдельные стартовые пути трёх ролей, политика свободной регистрации и правило передачи fallback сотруднику.

## Почему появлялся огромный список

Источник не являлся ошибкой рендера.

- В исходной версии `TrajectoryConstructor.jsx` состояние `activeTab` по умолчанию было равно `existing`.
- Компонент вызывал `getHistoryUsers()`, который делал запрос `GET /analysis/users`.
- Полученный массив целиком передавался в `<select>`.
- После загрузки автоматически выбирался `users[0]`.

Текущая версия устраняет доступ к реестру для Employee/Methodist и не загружает его без роли Admin. Целевой поиск закреплённых сотрудников остаётся зависимым от модели назначений.

## Критические проблемы

### P0. Фиктивная ролевая модель

**Исходное состояние:** всем пользователям выдавался `Methodist` в JWT.

**Текущий статус:** техническая часть исправлена — роль хранится в БД, JWT и `/me`; регистрация назначает минимальную роль `Employee`. Политика выдачи ролей через приглашения/SSO и административный интерфейс остаётся внешним продуктовым решением.

**Риск:** любой зарегистрированный пользователь выглядит как методист и получает доступ к действиям, которые могут быть предназначены только для сотрудника или администратора.

**Исправление:**

1. Добавить в сущность пользователя поле роли и миграцию БД.
2. Минимальный набор ролей: `Employee`, `Methodist`, `Admin`.
3. JWT должен содержать роль из БД, а не константу в коде.
4. Registration в production не должен самовольно назначать `Methodist`. Допустимые варианты:
   - учетные записи создает администратор;
   - пользователь получает приглашение с заранее назначенной ролью;
   - используется корпоративный SSO с маппингом групп на роли.
5. Frontend должен получить роль из безопасного endpoint сессии (`GET /me`) либо из подтвержденного claim и выбирать начальный маршрут по ней.

### P0. Реестр сотрудников доступен без предметного ограничения

**Исходное состояние:** `GET /analysis/users` возвращал полный набор профилей любому вошедшему пользователю.

**Текущий статус:** включена глобальная серверная авторизация, endpoint закрыт ролью Admin, Employee/Methodist получают 403, пользовательский frontend его не запрашивает. Серверный поиск закреплённых сотрудников нельзя реализовать до появления модели назначений.

**Риск:** раскрываются ФИО, должности, ведомства и история обучения. Для реальных сотрудников это недопустимо.

**Исправление:**

1. Настроить fallback authorization policy: все endpoint закрыты, кроме явно помеченных `[AllowAnonymous]` login, register (только для demo), health-check.
2. Добавить `[Authorize]` к контроллерам и ролевые/ресурсные политики к операциям.
3. Удалить из пользовательского API endpoint, который отдает весь файл-реестр.
4. Ввести серверный поиск сотрудников с ограничениями:
   - не искать до ввода 2-3 символов;
   - ограничивать результат, например 20 записями;
   - возвращать только поля, нужные для выбора: id, ФИО, должность, ведомство;
   - детальную историю отдавать только после выбора конкретного доступного сотрудника;
   - выполнять проверку области доступа до поиска, а не на frontend.
5. Полный импорт/просмотр реестра оставить только администратору в отдельном административном сценарии.

### P0. Нет привязки между учетной записью и сотрудником

**Текущее состояние:** пользователь, вошедший в систему, и сотрудник из реестра остаются разными, несвязанными сущностями. Реализация требует утверждённых правил привязки и назначений.

**Риск:** невозможно обеспечить «сотрудник видит только себя» или «методист видит только закрепленных».

**Исправление:**

1. Добавить сущность `EmployeeProfile` с устойчивым внутренним ID, не зависящим от ФИО.
2. Добавить связь `User.EmployeeProfileId` для роли `Employee`.
3. Добавить таблицу назначений `MethodistEmployeeAssignment` или политику по подразделениям `MethodistDepartmentAssignment` для роли `Methodist`.
4. Все запросы к профилю, истории, результату, выгрузке и повторному анализу должны проверять ресурсную авторизацию по этому ID.
5. Не использовать ФИО как ключ связи или правило доступа: оно не уникально и может измениться.

### P0. Результат fallback может восприниматься как полноценный AI-анализ

**Исходное состояние:** при ошибке LLM детерминированная ИОТ могла восприниматься как полноценный результат.

**Текущий статус:** контракт качества, `CompletedWithLimitations`, явная UI-маркировка и запрет экспорта реализованы. Остаётся выбрать продуктовое правило: подтверждение методиста или окончательный `Failed`.

**Риск:** методист или сотрудник может экспортировать упрощенный подбор как экспертную персональную рекомендацию.

**Исправление:**

1. Расширить контракт результата: `generation_mode` (`llm` / `fallback`), `quality_status` (`verified` / `degraded` / `failed`), `model_version`, `catalog_version`, `generated_at`.
2. Добавить отдельный статус задачи `CompletedWithLimitations`.
3. В UI и при экспорте явно маркировать degraded-результат.
4. Для production принять одно из правил:
   - fallback требует подтверждения методиста перед передачей сотруднику и экспортом;
   - fallback переводится в `Failed` и пользователь делает повторный запуск.
5. Перед запуском проверять доступность выбранного провайдера/модели; недоступную модель не предлагать пользователю.

### P1. Фоновые задачи могут потеряться при перезапуске API

**Исходное состояние:** генерация запускалась через `Task.Run` в API-процессе.

**Текущий статус:** реализована стойкая PostgreSQL-очередь и `AnalysisQueueWorker`; незавершённая задача переживает рестарт, зависший `Processing` восстанавливается, штатная остановка не расходует попытку.

**Риск:** после рестарта контейнера отчет останется `Processing`, а работа не возобновится.

**Исправление:**

1. Создать стойкую очередь задач в БД или Redis.
2. Выполнение перенести в отдельный worker или `BackgroundService`, не запускать фоновые задачи из HTTP-контроллера.
3. Состояния: `Queued`, `Processing`, `Completed`, `CompletedWithLimitations`, `Failed`, `Retrying`, `Cancelled`.
4. Хранить количество попыток, `next_retry_at`, код/безопасное сообщение ошибки, модель и снимок входных данных.
5. При старте worker искать зависшие `Processing` задачи и переводить в retry либо failed.
6. Использовать идемпотентный ключ, чтобы двойной клик или повтор сетевого запроса не создавал две ИОТ.

## Целевая ролевая модель

| Роль | Начальный экран | Права |
|---|---|---|
| `Employee` | «Моя траектория» | Видит только свой профиль, свои ИОТ и экспорт своих отчетов; может актуализировать разрешенные поля и запросить пересчет для себя. |
| `Methodist` | «Мои сотрудники» | Ищет только закрепленных сотрудников/подразделения; создает, просматривает и корректирует их ИОТ; видит историю своих кейсов. |
| `Admin` | «Управление системой» | Управляет пользователями, ролями, назначениями, импортом реестра, каталогом, доступностью моделей и аудитом. |

Роль не является визуальным ярлыком. Она должна ограничивать серверные данные и доступные операции.

## Целевые пользовательские пути

### Сотрудник

1. Входит через корпоративную учетную запись/приглашение.
2. Сразу видит свою актуальную ИОТ либо пустое честное состояние «Траектория еще не сформирована».
3. Проверяет только свой профиль и историю обучения.
4. Запрашивает генерацию или повторный анализ для себя.
5. Просматривает этапы, основания, ограничения и экспортирует свой отчет.

**Сотрудник никогда не видит общий реестр людей.**

### Методист

1. Входит и видит рабочий список собственных кейсов, а не полный реестр.
2. Нажимает «Найти сотрудника».
3. Вводит ФИО, должность или ведомство; получает ограниченные результаты только в пределах доступа.
4. Открывает карточку сотрудника, проверяет профиль и историю.
5. Создает ИОТ, следит за статусом задачи, изучает результат.
6. При degraded fallback подтверждает результат или перезапускает анализ согласно выбранному правилу.

### Администратор

1. Управляет импортом справочников и каталогов отдельно от конструктора ИОТ.
2. Создает пользователей, назначает роли и закрепления.
3. Видит технические ошибки и аудит, но не получает неограниченный доступ к содержимому отчетов без отдельной политики.

## Требования к API

### Аутентификация и сессия

- `POST /auth/login` - возвращает токен и минимальную информацию о сессии.
- `POST /auth/register` - только demo-режим или по приглашению; в production отключается/ограничивается.
- `GET /me` - текущий пользователь: id, имя, роль, доступные действия, привязанный employee profile при наличии.
- Refresh-token или другой согласованный механизм обновления сессии; logout должен аннулировать клиентскую сессию.

### Сотрудники

- `GET /employees/search?q=...` - только для методиста/admin, с проверкой области доступа, ограничением выдачи и пагинацией.
- `GET /employees/{id}` - детальная карточка, только при разрешении на конкретный ресурс.
- `GET /me/employee` - только для сотрудника; исключает необходимость искать самого себя.
- Никакого `GET /analysis/users`, отдающего весь реестр, в пользовательском контуре.

### ИОТ и отчеты

- Создание ИОТ принимает `employee_id` или разрешенный профиль, а backend проверяет права до постановки задачи.
- `GET /analysis/status/{taskId}` проверяет владельца отчета либо ресурсное назначение методиста.
- История возвращает только доступные пользователю отчеты.
- Экспорт проверяет те же права, что просмотр результата.
- В ответах всегда отдается честный статус качества генерации.

### Администрирование

- Импорт данных, назначение ролей, привязка сотрудников, управление каталогом и модельными настройками вынести в `/admin/*` и закрыть политикой Admin.
- Все административные действия логировать.

## Миграция и переходный план

### Этап 1. Немедленное закрытие рисков

1. Включить глобовую авторизацию и явно оставить публичными только login/register/health.
2. Закрыть или временно отключить endpoint полного реестра.
3. Убрать автоматическую загрузку и выбор первого сотрудника в конструкторе.
4. Перевести стартовый экран в нейтральный: «Создать ИОТ по новому профилю» для demo или «Мои сотрудники» после внедрения ролей.
5. Пометить fallback-результаты и запретить их бесшовный экспорт до решения продукта.

### Этап 2. Данные и роли

1. Добавить миграции пользователей, ролей, профилей сотрудников и назначений.
2. Импортировать существующий реестр в `EmployeeProfile`, сформировать стабильные ID.
3. Назначить администратора вручную через безопасную миграцию/CLI.
4. Создать первоначальные назначения методистов на сотрудников или подразделения.
5. Выпустить `GET /me` и ресурсные authorization policies.

### Этап 3. Frontend-пути

1. Сохранить роль в состоянии сессии.
2. Реализовать три стартовых маршрута и меню по правам.
3. Заменить dropdown всего реестра на серверный поиск.
4. Сделать «Моя траектория» единственным стартовым путем сотрудника.
5. Сделать список текущих кейсов и поиск сотрудника стартовым путем методиста.

### Этап 4. Надежность задач

1. Внедрить устойчивую очередь/worker.
2. Добавить повтор, восстановление и идемпотентность.
3. Подключить мониторинг ошибок модели и доли fallback.

## Критерии приемки

- Обычный сотрудник после входа не получает список других сотрудников и не может запросить его через API.
- Методист не может найти или открыть профиль вне своего назначения.
- Администратор получает доступ только через отдельный защищенный контур.
- JWT отражает фактическую роль пользователя из БД; никакой роли `Methodist` по умолчанию для всех.
- Все контроллеры, кроме явно публичных, требуют авторизацию.
- Запросы к профилям, отчетам, статусам, истории и экспорту проверяют доступ к конкретному ресурсу на backend.
- Первый экран зависит от роли и дает одну понятную рабочую задачу.
- В конструкторе нет загрузки полного реестра и автоматической подстановки чужого профиля.
- Fallback-результат невозможно спутать с полноценным LLM-анализом.
- После рестарта API незавершенная задача не остается бессрочно в `Processing`.
- Проведены интеграционные тесты на запрет доступа: employee-to-employee, methodist-to-unassigned-employee, user-to-admin, anonymous-to-protected-endpoint.
- Проведен ручной UX-проход каждого из трех пользовательских путей на desktop и mobile.

## Что нельзя делать

- Не ограничиваться скрытием dropdown на frontend: пользователь все равно сможет получить данные через API.
- Не передавать роль из скрытого UI-поля или доверять роли из входящего запроса.
- Не использовать ФИО как идентификатор сотрудника.
- Не оставлять свободную регистрацию с ролью методиста на production-стенде.
- Не отображать «успешно сформировано» для fallback без явного статуса качества.
- Не хранить в технических логах полные персональные данные, исходные файлы и токены.

## Решение, необходимое от владельца продукта

До начала этапа 2 требуется зафиксировать:

1. Сотрудник сам формирует ИОТ или только просматривает подтвержденную методистом?
2. Методист получает доступ по списку закрепленных людей или по подразделениям?
3. Нужна ли свободная регистрация на production, или используются приглашения/SSO?
4. Может ли fallback быть доступен сотруднику, или его обязательно подтверждает методист?

Без этих четырех решений нельзя корректно реализовать права, но этап 1 можно выполнить немедленно.
