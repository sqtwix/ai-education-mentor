# Передача заказчику и сценарий презентации платформы ИОТ

Дата актуализации: 20 сентября 2026 года.

## 1. Статус и границы готовности

Платформа реализует технический контур формирования индивидуальной образовательной траектории (ИОТ): учетная запись, ввод или загрузка профиля, выбор доступного AI-провайдера, стойкая очередь, проверка результата по официальному каталогу, история, архив и экспорт проверенного результата.

Решение готово к пилоту в закрытом контуре после успешного контейнерного release gate на целевом сервере. Называть его полностью готовым к корпоративной промышленной эксплуатации пока нельзя по двум причинам:

1. владелец продукта не утвердил связь учетной записи с карточкой сотрудника, назначения методистов, политику свободной регистрации/SSO и правило согласования резервной траектории;
2. текущий аудит выполнен на хосте без запущенного Docker Engine, поэтому чистый Compose deploy, PostgreSQL migration, runtime ACL, backup/restore и реальный browser E2E должны быть повторены на приемочном сервере.

Это не скрытые дефекты. Техническая часть ограничения ролей уже безопасна по умолчанию: новая учетная запись получает `Employee`, полный реестр доступен только `Admin`, а отчеты изолированы по владельцу. Но целевые пути «сотрудник видит только свою карточку» и «методист видит закрепленных сотрудников» требуют продуктовой модели назначений, которой пока нет.

## 2. Какую проблему решает продукт

Ручное составление ИОТ требует одновременно учитывать профиль служащего, должность, ИОГВ, карьерную цель, пройденные программы, каталог и статистику коллег. Платформа собирает эти источники в один проверяемый процесс и сокращает рутинную работу методиста.

Ценность решения:

- пройденные программы автоматически исключаются;
- рекомендовать можно только программу из локального официального каталога;
- каждому курсу сопоставляются факты каталога и доступные основания;
- неполный или резервный результат явно получает `CompletedWithLimitations` и не экспортируется как финальная ИОТ;
- локальный режим позволяет не передавать профиль за пределы закрытого Docker-контура;
- история и очередь переживают перезапуск приложения.

Платформа помогает принять решение, но не заменяет методиста и не доказывает семантическую точность без экспертно размеченного набора.

## 3. Пользователи, роли и сценарии

### Фактически реализовано

| Роль | Фактические права |
|---|---|
| `Employee` | Регистрируется, создает ИОТ по введенному/загруженному профилю, видит только собственные задачи и настройки. |
| `Methodist` | Роль поддерживается в JWT/БД, но назначения сотрудников и отдельный рабочий список еще не реализованы. |
| `Admin` | Получает полный реестр через защищенный endpoint и агрегированные операционные метрики. Роль не выдается публичной регистрацией. |

Все controller-endpoint, кроме login/register и health, требуют JWT. Status, history, rename, archive и unarchive фильтруются по `UserId`; запрос чужой задачи возвращает `404`, не раскрывая ее существование.

### Целевая корпоративная модель

- Сотрудник входит через приглашение/SSO, видит свою карточку и свои ИОТ.
- Методист видит только назначенных сотрудников или разрешенные подразделения.
- Администратор управляет ролями, назначениями, импортом и аудитом в отдельном контуре.

До реализации нужно письменно утвердить:

1. может ли сотрудник самостоятельно запускать пересчет;
2. назначения методиста задаются списком сотрудников или подразделениями;
3. свободная регистрация отключается, заменяется приглашениями или SSO;
4. `CompletedWithLimitations` становится `Failed` либо проходит подтверждение методиста.

## 4. Данные и жизненный цикл анализа

В репозитории находятся 159 программ каталога 2025 года: 95 ППК и 64 электронных курса. Реестр истории содержит 1 314 записей по 323 профилям, 36 должностям и 60 ИОГВ.

Поддерживаемые входы: ручной JSON-контракт, `.json`, `.csv`, `.xlsx`, `.xls` и `.zip`. Загруженный реестр обрабатывается целиком и может содержать до 500 профилей. Ограничения по умолчанию: 25 МБ на файл, 50 МБ на запрос, 20 файлов; для ZIP/XLSX проверяются число entries, распакованный объем и степень сжатия.

Жизненный цикл:

1. API валидирует тип, размер и структуру данных.
2. Нормализованный снимок входа и выбранная модель сохраняются в PostgreSQL.
3. Задача получает `Queued`; worker атомарно забирает ее через `FOR UPDATE SKIP LOCKED`.
4. Для каждого профиля AI Driver запускает три роли: анализ сигналов развития, выбор кандидатов, обоснование.
5. Сервер повторно проверяет курсы по каталогу, удаляет дубли и пройденные программы, не публикует неподтвержденные числовые уровни и сроки.
6. После каждого профиля batch сохраняется checkpoint.
7. Финал: `Completed`, `CompletedWithLimitations` или `Failed`; временный сбой переводит задачу в `Retrying` с ограниченным числом попыток.
8. Проверенный результат доступен в истории и экспортируется в PDF, XLSX и JSON. Резервный результат экспортировать нельзя.

Когортный бенчмарк отключен, пока владелец данных не задаст `MIN_COHORT_SIZE`. После утверждения сначала используется точная пара `должность + ИОГВ`; расширение до той же должности по городу должно сопровождаться limitation. Поиск «смежной должности» по подстроке запрещен.

## 5. Архитектура и поток данных

```text
Браузер
  -> nginx / React 19
     -> /api/v1, JWT
        -> ASP.NET Core 9
           -> PostgreSQL 15: users, analysis_reports, очередь, checkpoint
           -> FastAPI AI Driver
              -> DeepSeek API (опционально, обезличенный профиль)
              -> GigaChat API (опционально, обезличенный профиль)
              -> local_llm / OpenAI-compatible
                 -> managed llama.cpp + GGUF либо внешний endpoint
```

Компоненты:

- `frontend`: SPA, навигация, формы, статусы, каталог, аналитика, настройки и клиентский экспорт; nginx проксирует `/api/`.
- `api-core`: auth, ACL, валидация загрузок, каталог/бенчмарки, стойкая очередь, история и операции над отчетами.
- `ai-driver`: трехролевой LLM-конвейер, PII-маскирование, grounding и детерминированный безопасный fallback.
- `postgres`: пользователи, настройки, входной снимок, статусы, checkpoint и результат.
- `local-llm`: опциональный профиль `local-ai`; наружу не публикуется.

Основные API:

- `POST /api/v1/auth/register`, `POST /api/v1/auth/login`;
- `GET /api/v1/me`, `GET|PUT /api/v1/user/settings`;
- `POST /api/v1/analysis/generate-trajectory`, `POST /api/v1/analysis/upload`;
- `GET /api/v1/analysis/status/{taskId}`, `/history`, `/catalog`, `/benchmarks`, `/models`;
- `PUT /api/v1/analysis/rename/{taskId}`, `/archive/{taskId}`, `/unarchive/{taskId}`;
- `GET /api/v1/operations/metrics` — только `Admin`;
- `/health` — liveness, `/health/ready` — PostgreSQL + AI Driver readiness.

## 6. AI-пайплайн и выбор модели

Три роли не являются тремя независимыми источниками истины. Каталог остается источником фактов:

1. `competency-analyst` выделяет только наблюдаемые сигналы профиля и истории;
2. `trajectory-architect` выбирает кандидатов из ограниченного контекста, предварительно ранжированного по всему каталогу;
3. `trajectory-justifier` формирует методическое объяснение, после чего сервер снова проверяет результат.

### Почему эталонный локальный профиль — Qwen3-1.7B-Q4_K_M

Код и документы фиксируют его как воспроизводимый эталон managed GGUF: файл, SHA-256, context 4096, 4 threads, batch 512, parallel 1 и закрепленный digest llama.cpp. Практические преимущества для пилота:

- обработка внутри закрытого контура и предсказуемая приватность;
- нет оплаты за токены и зависимости от внешнего API;
- русский язык и OpenAI-compatible chat contract;
- умеренные требования к CPU/RAM для демонстрационного/ограниченного режима.

Компромиссы: CPU latency выше, малая модель чаще дает невалидный/неполный ответ, возможен `CompletedWithLimitations`, пропускная способность ограничена последовательной очередью. Серверная проверка снижает риск публикации выдуманных каталожных фактов, но не превращает слабую модель в экспертную.

DeepSeek и GigaChat поддержаны архитектурой, но без ключей и gold dataset их качество, стоимость и latency не измерены. `MODEL_COMPARISON.md` намеренно оставляет метрики `TBD`. Поэтому корректный вывод для заказчика:

> Локальная Qwen выбрана как воспроизводимый приватный baseline, а не как доказанный победитель по качеству. Финальный выбор делается после одинакового прогона Qwen, DeepSeek и GigaChat на экспертно размеченном наборе.

Критерии сравнения: отсутствие повторов, доля каталожно валидных курсов, JSON schema validity, совпадение когорты, покрытие evidence, PII safety, median/p95 latency, стоимость и экспертная полезность.

## 7. Безопасность и эксплуатационные свойства

- Пароли хешируются ASP.NET Identity PasswordHasher; длина новых паролей 12–128 символов.
- JWT проверяет issuer, audience, lifetime и HMAC; секрет не короче 32 байт, expiry 5–10 080 минут.
- Публичная регистрация создает только `Employee`; `Admin` публично не выдается.
- Профиль внешнего провайдера получает псевдоним вместо ФИО; email, телефон, СНИЛС и паспортные шаблоны маскируются.
- Входные поля и история имеют серверные пределы; пользовательские настройки — JSON-объект до 64 КБ.
- ZIP/XLSX защищены от чрезмерной распаковки; временные каталоги очищаются.
- API Core и AI Driver запускаются не от root, с read-only filesystem, `tmpfs` и `no-new-privileges`.
- PostgreSQL и managed LLM доступны только во внутренней сети; API и AI Driver публикуются на loopback.
- Логи ротируются по 5 файлов × 10 МБ; запросы логируются без body и токенов, с correlation id.
- Frontend отправляет CSP, `nosniff`, frame denial, referrer и permissions policy.

Перед доступом из внешней сети обязательны TLS reverse proxy/WAF, корпоративный ACL, секрет-хранилище, отключение или регламент свободной регистрации и согласованная политика ПДн.

## 8. Развертывание, конфигурация и проверка

Требования: Docker Engine 24+, Compose v2, минимум 4 CPU/8 ГБ RAM для режима без модели. Для эталонной managed GGUF ориентир — 8 CPU, 16 ГБ RAM и 20 ГБ SSD.

```bash
git clone https://github.com/sqtwix/ai-education-mentor.git
cd ai-education-mentor
chmod +x deploy.sh
./deploy.sh
```

Первый запуск создает `.env`, генерирует `DB_PASSWORD` и `JWT_SECRET`, устанавливает права `600`. Повторный deploy сохраняет существующие секреты и volumes. Не используйте `docker compose down -v`.

Минимальная приемочная проверка:

```bash
docker compose ps
curl -fsS http://127.0.0.1:5050/health/ready
curl -fsS http://127.0.0.1:8000/health
curl -fsS http://127.0.0.1:8000/models/availability
./scripts/no_ai_runtime_smoke.sh
./scripts/platform_runtime_smoke.sh
./scripts/qa_acl_smoke.sh
./scripts/backup_restore_smoke.sh
```

Для включенной локальной модели дополнительно:

```bash
docker compose --profile local-ai ps
./scripts/iot_runtime_smoke.sh
./scripts/iot_multi_user_runtime_smoke.sh
./scripts/iot_large_runtime_smoke.sh
```

Точные переменные и четыре режима провайдеров описаны в `README.md`, `env_example.txt` и `ADMIN_GUIDE.md`. Managed-файл принимается только при совпадении SHA-256; deploy выполняет минимальный chat inference.

## 9. Мониторинг, backup и восстановление

Контролировать:

- `unhealthy`, restart count, OOM и заполнение диска;
- длину очереди, возраст старейшей задачи, retries и длительность;
- долю `CompletedWithLimitations` и `Failed`;
- latency моделей и частоту отказов провайдеров;
- рост БД и успешность проверяемых backup.

Admin-метрики: `GET /api/v1/operations/metrics` с JWT роли `Admin`.

Backup создается `pg_dump`, хранится вне Docker host и шифруется. `scripts/backup_restore_smoke.sh` восстанавливает dump во временную БД, сверяет данные и удаляет только временную БД. Для disaster recovery нужны согласованная копия БД, защищенный `.env`, Data Protection keys и зафиксированные image/model digests.

Откат:

1. остановить пользовательский трафик;
2. сохранить новый диагностический backup;
3. развернуть зафиксированные предыдущие образы/commit;
4. при несовместимой миграции восстановить согласованный backup БД;
5. проверить readiness, ACL и контрольный профиль до открытия трафика.

## 10. Сценарий живой презентации на 6–8 минут

### 0:00–0:45 — проблема

Показать титульный экран. Сказать: «Методисту нужно сопоставить профиль, историю обучения, каталог и опыт коллег. Мы превращаем это в один проверяемый процесс, но сохраняем экспертный контроль».

### 0:45–1:30 — данные и доверие

Показать каталог и аналитику. Объяснить: 159 реальных программ, 1 314 записей истории; модель не может добавить курс вне каталога, а пройденное исключается.

### 1:30–3:30 — живой сценарий

1. Войти тестовой учетной записью.
2. Открыть «Создать индивидуальную траекторию».
3. Выбрать «Новый профиль» и заполнить ФИО, должность, ИОГВ, цель.
4. Добавить одну пройденную программу.
5. Показать фактическую доступность моделей; выбрать только `ready`.
6. Запустить ИОТ и показать серверные стадии без вымышленного таймера.
7. Открыть результат: курсы, основания, evidence и limitations.
8. Проверить, что пройденной программы нет.

Фраза при fallback: «Это не скрытая ошибка: система честно пометила результат как требующий эксперта и отключила финальный экспорт».

### 3:30–4:45 — batch и устойчивость

Загрузить `TEST_PROFILE_IOT.json`, затем один предоставленный XLSX. Пояснить лимит 15 профилей, checkpoint после каждого сотрудника, retry после перезапуска и идемпотентный `requestId`.

### 4:45–5:45 — история и экспорт

Показать историю, переименование, архив/восстановление и экспорт `Completed` в PDF, XLSX, JSON. Не демонстрировать экспорт degraded-результата как успешный.

### 5:45–6:45 — архитектура и приватность

Показать схему этого документа. Сказать: «Для managed GGUF профиль не покидает контур; для внешней модели ФИО заменяется псевдонимом, а типовые ПДн маскируются».

### 6:45–8:00 — эффект и следующий шаг

Назвать KPI пилота и предложить экспертную приемку трех моделей. Не обещать проценты экономии до измерения baseline.

## 11. KPI и бизнес-эффект пилота

Измерять, а не предполагать:

- медианное время методиста на одну ИОТ до/после;
- доля ИОТ, принятых без изменения и после одной корректировки;
- 0-repeat rate для пройденных программ;
- catalog validity и evidence coverage;
- доля `Completed`, `CompletedWithLimitations`, `Failed`;
- median/p95 полного времени генерации;
- число инцидентов доступа/утечки ПДн — целевое значение 0;
- стоимость одной принятой ИОТ по каждому провайдеру;
- удовлетворенность методистов и сотрудников по согласованной анкете.

Экономический эффект рассчитывается после двух недель baseline и пилота: `(старое время − новое время) × число ИОТ × стоимость часа`, отдельно учитываются инфраструктура, экспертная проверка и стоимость внешних API.

## 12. Частые вопросы и ответы

**Почему не просто чат с моделью?** Потому что чат не дает стойкую очередь, ACL, исключение пройденного, проверку каталога, checkpoint, историю и контролируемый экспорт.

**Может ли модель выдумать курс?** Она может предложить текст, но сервер не публикует курс, которого нет в каталоге, и восстанавливает фактические поля из локального справочника.

**Почему иногда нет бенчмарка?** `MIN_COHORT_SIZE` должен утвердить владелец данных. До этого система не превращает малую группу в сомнительное доказательство.

**Почему Qwen?** Это приватный и воспроизводимый baseline. Превосходство по смысловому качеству не заявляется до gold dataset.

**Что происходит при падении сервиса?** Вход и checkpoint остаются в PostgreSQL; задача переходит в retry и возобновляется. После исчерпания попыток — `Failed` с безопасным сообщением.

**Можно ли использовать облако?** Да, после договора, лимитов, политики хранения и проверки ключа. Профиль псевдонимизируется, но юридическое согласование все равно обязательно.

**Где SSO и назначения методистов?** Это следующий обязательный этап корпоративной интеграции после четырех продуктовых решений из раздела 3.

## 13. План пилота

1. Утвердить владельца данных, роли, `MIN_COHORT_SIZE`, правило fallback и политику ПДн.
2. Подготовить 15–30 обезличенных профилей с экспертной разметкой допустимых/запрещенных рекомендаций.
3. Развернуть изолированный стенд, выполнить весь `RELEASE_GATE.md` и backup/restore.
4. Сравнить Qwen, DeepSeek и GigaChat одним скриптом, prompt/version/temperature/commit.
5. Провести пилот с 3–5 методистами и ограниченной группой сотрудников.
6. Еженедельно разбирать degraded/failed и экспертные корректировки.
7. Принять решение о модели и масштабе только по KPI.

Критерии успешности должны быть численно утверждены до пилота. Без утвержденных порогов «пилот успешен» не является проверяемым заключением.

## 14. Чек-лист сдачи и интеграции

- [ ] Продуктовые решения по ролям, регистрации/SSO, назначениям и fallback подписаны.
- [ ] TLS, домен, ACL/WAF и секрет-хранилище настроены.
- [ ] `.env` не содержит шаблонных секретов; рабочие секреты отсутствуют в Git.
- [ ] Миграции применены на копии production backup.
