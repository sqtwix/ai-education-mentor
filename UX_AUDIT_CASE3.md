# UX-аудит и ТЗ на упрощение интерфейса Case 3

**Статус:** документ для агента, который будет перерабатывать интерфейс.

**Цель:** сделать текущую систему анализа образовательной траектории понятной с первого входа, спокойной для регулярной работы и пригодной для экранов от мобильного до широкого рабочего монитора. Функциональность, маршруты, данные и бизнес-логика должны остаться прежними.

## Жесткие границы работ

- Не добавлять новые продуктовые функции, сущности, сценарии, разделы или API.
- Не добавлять моковые отчеты, фиктивные метрики, демонстрационные карточки, заглушки с выдуманными данными и «примерные» результаты.
- Не менять смысл генерации ИОТ, правила выбора модели, экспорт, роли, авторизацию и контракты backend API без отдельного решения продукта.
- Не удалять существующие реальные сценарии: выбор сотрудника, новый профиль, загрузка файла, выбор модели, запуск анализа, история, каталог, бенчмарки, настройки доступности, PDF/XLSX/JSON-экспорт.
- Не превращать внутреннюю систему в лендинг, не добавлять декоративные фоны, градиентные пятна, иллюстрации или маркетинговые блоки.
- Не скрывать важную ошибку, ограничение модели или отсутствие данных. Их надо показывать короче и только в момент, когда это влияет на действие или понимание результата.

## Критерий успеха

Пользователь после входа за 30 секунд должен ответить на три вопроса: «что здесь можно сделать», «с чего начать» и «что получится в результате». Основной путь должен читаться так:

`Выбрать источник данных -> проверить профиль -> запустить анализ -> изучить ИОТ -> при необходимости экспортировать`.

Сейчас этот путь существует, но он растворяется среди истории, счетчиков, технических описаний агентов, карточек модели, предупреждений и повторяющихся плашек.

## Итог аудита

### P0. Нет единственного очевидного следующего действия

**Где:** главный экран после входа, `TrajectoryConstructor.jsx`, `Layout.jsx`.

**Наблюдение:** пользователь сразу видит боковую историю, несколько пунктов навигации, крупный вводный блок, статистику, три режима подготовки данных, форму, историю обучения, выбор модели и описание пайплайна. Визуально все элементы выглядят значимыми. Кнопка генерации не получает достаточного приоритета.

**Риск:** новый пользователь не понимает, нужно ли сначала выбирать сотрудника, загружать файл, читать про модель, открывать каталог или изучать историю.

**Требование:**

- Сделать главным содержанием экрана короткий заголовок «Создать индивидуальную траекторию» и один основной сценарий ввода.
- Оставить на первом экране только необходимое для запуска: режим источника данных, данные профиля выбранного режима и одно ясное действие «Сформировать ИОТ».
- Метрики, подробности модели, методику и историю обучения не должны конкурировать с формой на первом экране.
- Второстепенные данные переместить ниже по странице или раскрывать по явному действию пользователя.

### P0. Экран конструктора перегружен параллельными уровнями интерфейса

**Где:** `frontend/src/components/TrajectoryConstructor.jsx`.

**Наблюдение:** в одной рабочей области одновременно находятся режимы, поля профиля, чипы истории, ручное добавление курса, загрузка файлов, три карты моделей и описание внутренних этапов ИИ.

**Риск:** высокая когнитивная нагрузка, ошибки в заполнении, чувство «сложной системы» до первого результата.

**Требование:**

- Сохранить три существующих режима, но показывать только интерфейс выбранного режима. Не оставлять элементы других режимов рядом «на всякий случай».
- Режимы оформить как компактный сегментированный переключатель с короткими названиями: «Из базы», «Новый профиль», «Файл». Убрать из них счетчики, длинные подписи и технические расширения, если формат принимаемого файла уже указан у поля загрузки.
- Для профиля использовать одну спокойную двухколоночную сетку на desktop и одну колонку на mobile. Метки краткие, примеры только как placeholder.
- Историю обучения показывать компактно: видимые выбранные записи и действие добавления. Ручное добавление раскрывать только после нажатия, а не держать постоянной строкой в форме.
- Подробное описание ИИ-конвейера убрать из основной области в раскрываемый блок «Как формируется рекомендация». Он должен быть закрыт по умолчанию.
- Блок выбора модели оставить, но сделать компактным. Детали провайдера, скорости и технические ограничения показывать после выбора или во всплывающем описании, не тремя одинаково крупными карточками.
- Основную кнопку закрепить в логичном завершении формы; на длинном экране допустима липкая нижняя панель только на мобильных устройствах.

### P0. Технический язык показывается до пользовательской задачи

**Где:** `TrajectoryConstructor.jsx`, `TrajectoryRoadmap.jsx`, тексты моделей и пайплайна.

**Наблюдение:** пользователь видит названия внутренних агентов, провайдеров и механик раньше, чем получает ответ на свою прикладную задачу.

**Риск:** система выглядит экспериментальной и сложной, хотя пользователь ожидает сервис подбора обучения.

**Требование:**

- В основных сценариях использовать пользовательские формулировки: «Модель анализа», «Источник рекомендаций», «Основание рекомендации».
- Не показывать названия внутренних агентов, цепочек обработки и служебные идентификаторы без явного раскрытия «Технические детали».
- Не менять реальные сведения о модели и ограничениях, только менять их место и уровень детализации.

### P0. Результат ИОТ начинаетcя с избытка вторичной информации

**Где:** `frontend/src/components/TrajectoryRoadmap.jsx`.

**Наблюдение:** шапка результата содержит экспорт, баннер сотрудника, несколько счетчиков, AI-резюме, ограничения, переключатели этапов и боковые аналитические блоки. Каждая карточка курса также повторяет много типов данных.

**Риск:** пользователь не может быстро увидеть сам маршрут обучения и причины выбора курсов.

**Требование:**

- Верх результата: название ИОТ, сотрудник, краткий итог в одну-две строки и компактные действия экспорта. Не использовать текстовые кнопки там, где понятна иконка с tooltip.
- Основной контент: последовательность этапов и курсы. Активный этап должен считываться с первого взгляда.
- Карточка курса в свернутом состоянии: название, организация/формат при наличии, длительность, приоритет и одно короткое основание. Компетенции, полное обоснование, источники и дополнительные метаданные показывать по раскрытию или в существующей модальной карточке.
- Ограничения и неполнота данных: одно ненавязчивое сообщение возле резюме, если они влияют на достоверность результата. Не дублировать их внутри каждого блока.
- Радар и бенчмарк не должны занимать главный фокус. Показывать их в правой колонке на широком экране и после основного маршрута на узком. При отсутствии реальных данных оставлять честное короткое состояние, без декоративной имитации графика.

### P1. Боковая панель конкурирует с рабочей задачей

**Где:** `frontend/src/components/Layout.jsx`.

**Наблюдение:** бренд, кнопка создания, навигация, поиск и полный список истории располагаются в одной колонке. При первом входе история может стать визуально заметнее текущего действия.

**Требование:**

- В боковой панели оставить: бренд, одно главное действие, основные разделы и компактный блок истории.
- Историю по умолчанию ограничить несколькими последними элементами и действием «Вся история» или существующим переходом в архив. Не прятать данные, а не занимать ими весь экран.
- Поиск по истории показывать только в контексте истории/архива или раскрывать по иконке.
- На mobile панель должна закрываться после перехода и не перекрывать содержимое.

### P1. Плашки, бейджи и карточки используются чаще, чем нужно

**Где:** почти все компоненты и `frontend/src/index.css`.

**Наблюдение:** статусы, типы, счетчики, компетенции, источники, ограничения и действия часто оформлены отдельными плашками. Карточки вложены в карточки, а одинаковая визуальная тяжесть не дает понять, что главное.

**Требование:**

- У каждого элемента оставить только один визуальный контейнер. Не вкладывать карточку в карточку.
- Бейдж использовать только для статуса, который требует быстрого сканирования: например, «Готово», «Ошибка», «В процессе», уровень приоритета.
- Свойства курса и профиля собирать в обычную строку метаданных с разделителями, а не в набор плашек.
- Удалить декоративные счетчики и повторяющиеся подписи, если они не меняют действие пользователя.
- Все предупреждения привести к одному компактному паттерну: иконка, одна фраза, при необходимости ссылка «Подробнее».

### P1. Типографика и масштабирование не имеют четкой системы

**Где:** `frontend/src/index.css`.

**Наблюдение:** CSS разросся примерно до 5 800 строк; в нем много перекрывающихся переменных, тематических и адаптивных правил. Размеры заголовков и служебного текста часто близки, из-за чего иерархия слабеет. В интерфейсе одновременно используются больше двух визуальных типографических ролей.

**Требование:**

- Оставить максимум две гарнитуры: одну UI-гарнитуру для всего интерфейса и одну только для специальных доступных/системных случаев, если она реально обязательна. Предпочтительно: `Inter` или системный sans-serif для UI; `Verdana` только как режим повышенной читаемости, а не как третья постоянная стилистика.
- Ввести конечную шкалу: 12, 14, 16, 20, 24, 32 px. Не масштабировать шрифт от ширины viewport.
- Использовать регулярное начертание для текста, medium/semibold только для названий и основных действий. Не использовать жирность как замену иерархии.
- Ввести единую шкалу отступов: 4, 8, 12, 16, 24, 32 px; радиус контейнеров не более 8 px.
- После переработки удалить неиспользуемые правила и дублирующие медиа-правила, а не накладывать новый слой CSS поверх старого.

### P1. Адаптивность построена вокруг сжатия плотного desktop-экрана

**Где:** `index.css`, `Layout.jsx`, конструктор, результат, каталог и аналитика.

**Риск:** на 390 px элементы будут либо слишком мелкими, либо многоуровнево наложенными; на 1366 x 768 пользователь увидит мало полезного из-за крупных вводных блоков.

**Требование:**

- Проектировать от информационной приоритизации, а не только от переноса колонок.
- Desktop: 1366 x 768 и 1440 x 900 должны показывать рабочее действие без необходимости прокручивать вводный текст.
- Mobile: 390 x 844, одна колонка, зона нажатия не менее 44 px, нет горизонтальной прокрутки, боковая панель не остается поверх формы.
- Таблицы, наборы фильтров и аналитика должны иметь предсказуемый mobile-паттерн: горизонтальная прокрутка только для данных, которые нельзя сократить; не для всей страницы.

### P1. Каталог и аналитика воспринимаются как перегруженные дашборды

**Где:** `CatalogExplorer.jsx`, `ColleagueAnalytics.jsx`, соответствующие части `Pages.jsx`.

**Требование:**

- Каталог: приоритет у поиска, фильтров и списка реальных программ. Уменьшить вводные тексты, свести фильтры в одну панель, использовать плотный список или таблицу вместо россыпи декоративных карточек.
- Аналитика: сверху короткий заголовок и выбранный срез, затем максимум несколько ключевых показателей. Развернутые пояснения к бенчмаркам и источникам показывать рядом с графиком по запросу.
- Не делать аналитику обязательным этапом создания ИОТ.

### P2. Настройки и режим доступности не должны создавать второй интерфейс поверх первого

**Где:** `AccessibilityToolbar.jsx`, `Pages.jsx`, `Layout.jsx`.

**Требование:**

- Сохранить все существующие настройки доступности.
- Не показывать большую панель постоянно. Открывать ее явным действием в шапке/настройках и закрывать после выбора.
- Настройки должны менять единые дизайн-токены, а не добавлять поверх страницы отдельные шрифты, размеры и плашки.

### P2. Тексты состояний и ошибок избыточны

**Где:** конструктор, генерация, загрузка, результаты.

**Требование:**

- Для загрузки: один статус, понятный прогресс и конкретная ошибка у соответствующего поля.
- Для генерации: название текущего этапа и честный статус, без описания внутренней архитектуры.
- Для пустых разделов: одна фраза, одно доступное действие. Не использовать длинные объяснительные карточки.
- Ошибка авторизации должна возвращать на вход без красных технических сообщений в рабочем интерфейсе.

## Карта целевого интерфейса

### После входа

1. Компактная боковая панель.
2. Заголовок «Создать индивидуальную траекторию» и короткая строка о результате.
3. Переключатель источника: «Из базы / Новый профиль / Файл».
4. Только поля выбранного источника.
5. Компактный выбор модели.
6. Основная кнопка «Сформировать ИОТ».
7. Ниже, вне первого фокуса: история обучения, методика и подробности.

### После формирования

1. Название результата, сотрудник, один итоговый текст.
2. Действия: экспорт в существующие форматы.
3. Этапы траектории и курсы как главный слой.
4. По запросу: подробности курса, доказательства, источники, компетенции.
5. Справа или ниже: бенчмарк и аналитика, только если для них есть реальные данные.

## Последовательность реализации

### Шаг 0. Зафиксировать инварианты

Перед визуальными правками составить список маршрутов, запросов, полей форм и состояний. Проверить, что все данные на экранах приходят из текущих API и не заменить их статическими примерами.

### Шаг 1. Основание дизайн-системы

Упростить `index.css`: типографика из двух гарнитур, шкалы размера/отступов, один паттерн кнопок, полей, статусов, модальных окон, карточек и предупреждений. Сначала удалить конфликтующие правила, затем применять токены в компонентах.

### Шаг 2. Каркас приложения

Переработать `Layout.jsx`: компактная навигация, ограниченная история, чистая верхняя панель, корректное поведение mobile-меню.

### Шаг 3. Конструктор ИОТ

Перестроить `TrajectoryConstructor.jsx` вокруг одного пошагового рабочего потока без добавления шагов в бизнес-логике. Свернуть технические детали и вторичные поля. Проверить все три источника данных, выбор модели и обработку ошибок.

### Шаг 4. Страница результата

Перестроить `TrajectoryRoadmap.jsx` вокруг этапов и курсов. Убрать дублирование плашек, перенести детальные сведения в раскрытие/существующую модаль, сохранить все реальные доказательства и ограничения.

### Шаг 5. Вторичные разделы

Упростить `CatalogExplorer.jsx`, `ColleagueAnalytics.jsx`, историю, архив и настройки без удаления данных или фильтров.

### Шаг 6. Регрессионная проверка

Проверить авторизацию, выбор существующего пользователя, новый профиль, JSON/XLSX-загрузку, запуск каждой доступной модели, историю, открытие результата, просмотр курса, каталог, бенчмарки, настройки, PDF/XLSX/JSON-экспорт, ошибки сети и истекшую сессию.

## Проверочные критерии приемки

- На первом экране после входа есть одно визуально главное действие: создание ИОТ.
- Пользователь может выбрать источник данных, заполнить профиль и запустить анализ без чтения технической справки.
- Максимум две гарнитуры во всех обычных состояниях интерфейса.
- В основной области не более одного уровня карточки; нет вложенных декоративных контейнеров.
- Технические названия агентов не видны без раскрытия деталей.
- У всех существующих функций сохранены реальные данные, обработка ошибок и доступы; моковые данные отсутствуют.
- Ограничения модели и отсутствие бенчмарка показаны честно, но не повторяются по экрану.
- Нет горизонтальной прокрутки и наложений на 390 x 844, 1366 x 768 и 1440 x 900.
- Работают клавиатурная навигация, видимый focus и режим доступности.
- `oxlint` и production-сборка frontend проходят; вручную проверены все сценарии из шага 6.

## Чего не считать завершением

- Простая смена цветов, теней и скруглений без изменения приоритета информации.
- Добавление еще одного режима, виджета, экскурсии, онбординга или интерактивной подсказки.
- Сокрытие реальных предупреждений вместо их краткой и контекстной подачи.
- Подмена каталога, метрик или результатов статическими «красивыми» данными.
- Добавление нового CSS поверх старого без очистки конфликтующих правил.

## Результат, который должен передать агент

1. Изменения frontend с сохранением всех текущих возможностей.
2. Краткий список удаленных визуальных шумов и перемещенных в progressive disclosure деталей.
3. Скриншоты ключевых экранов desktop и mobile с реальными данными.
4. Результаты lint/build и ручной регрессионной проверки.
5. Список замечаний, если какой-либо реальный сценарий нельзя упростить без продуктового решения.
